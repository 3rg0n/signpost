# 8. The viewer lives in this repository, with no JavaScript dependencies

## Status

Accepted. Supersedes [ADR 0006](0006-generator-and-viewer-are-separate-repositories.md).

## Context

[ADR 0006](0006-generator-and-viewer-are-separate-repositories.md) put the viewer in a
second repository. It rested on three claims, and the first one turned out to be wrong once
there was real output to look at.

**Claim one: a viewer worth using needs a JavaScript dependency tree.** 0006 states it
plainly — "anything good enough to be worth using needs dependencies the generator cannot
afford." Measured against what signpost actually emits, that does not hold. `signpost export
-format json` on this repository produces **23 nodes and 27 edges, across 3 node kinds and 2
edge kinds, with one confidence value**. A node-link view over a typed graph that small is a
few hundred lines of hand-written SVG: a Fruchterman-Reingold layout is about forty lines,
and the rest is filtering and a detail panel. The dependency tree 0006 was protecting the
generator from is not required to draw this. It would be required for a general-purpose
graph library that also handles a hundred thousand nodes, which is not what is being built.

**Claim two: the split is what keeps a broken viewer off the merge path.** This is the
load-bearing consequence in 0006, and it is true — but the repository boundary is not what
provides it. `.github/workflows/pages.yml` was already a separate workflow with its own
concurrency group and its own permissions, triggered independently of `ci.yml` and
`signpost.yml`. A Pages deploy that fails does not fail a merge today, and would not have
even if the viewer had always lived here. The isolation is a property of the **workflow
topology**, not of the repository count. 0006 attributed it to the wrong mechanism.

**Claim three: the injection surface should be isolated.** This one stands, and it survives
this decision intact. Interpolating untrusted repository strings — file paths, module names,
commit authors — into a rendered page is a real vulnerability class, and 0006's hardening
list is the right list. What changes is where it is enforced, not whether.

Against that, the split had a cost that 0006 named and accepted: "two repositories to
release and keep in step," with `graph.json` as a versioned contract between them. That cost
is paid immediately and in full, for a viewer that does not exist yet. A schema change in
the generator would need a coordinated release across two repositories before anyone had
ever looked at a rendered graph.

Two options were considered.

1. **Keep the split, build the viewer in `signpost-view`.** Honours 0006, and pays the
   two-repository coordination cost from day one to isolate a dependency tree that the
   measured graph size says is not needed.
2. **Build it here with no JavaScript dependencies.** Keeps the property 0006 was really
   defending — nothing in this repository's dependency governance changes — and drops the
   coordination cost. The injection surface moves here, so the hardening becomes a rule
   about this repository's `site/` directory rather than a rule about a repository.

## Decision

**The viewer is a component of this repository, hand-written, with zero JavaScript
dependencies.**

- It lives in `site/`, alongside the landing page, published by the existing `pages.yml`
  workflow. HTML, CSS, and hand-written JavaScript. **No `package.json`, no lockfile, no
  npm or pnpm in this repository.**
- The seam stays `graph.json`, generated by `signpost export -format json` at deploy time
  and never committed. The viewer treats it as untrusted input even though signpost
  generated it, because the repository it was generated *from* was untrusted.
- **The merge-path isolation is enforced by the workflow, not by the repository boundary.**
  `pages.yml` stays separate from `ci.yml` and `signpost.yml`, keeps `contents: read` at the
  top level, and is never a required check. A viewer that fails to build fails a deploy.
- 0006's hardening list is adopted verbatim as the rule for `site/`: escape everything,
  **no `innerHTML`**, a strict `Content-Security-Policy`, and no network egress from the
  page beyond the same-origin fetch of `graph.json`.

**The zero-dependency constraint is the whole decision, and it is what makes this
reversible.** If the viewer ever needs a real graph library, this ADR does not authorise
taking one: that is a new ADR, and the two-repository split in 0006 becomes the live option
again rather than a superseded one. The reason to write it down that way is that "we will
add just one small dependency" is exactly how the property in
[ADR 0002](0002-patchable-dependencies-not-zero-dependencies.md) decays.

**Two accepted ADRs assert the separate-repository claim and are not being edited.**
[ADR 0002](0002-patchable-dependencies-not-zero-dependencies.md) §Consequences says the
dependency gate "does not apply to the viewer" because the viewer is elsewhere, and
[ADR 0005](0005-commit-the-bundle-to-the-repository.md) §Consequences says "every JS
dependency lives in the separate viewer repository." Both stay as written, per the
immutability rule in [README](README.md): this ADR is the correction, and a reader who
follows the supersession chain gets the current answer. In substance the two statements
still hold — the dependency gate has nothing to gate, because there are no JavaScript
dependencies anywhere.

## Consequences

**The injection surface is now in the repository that gates merges, and that is the real
cost of this decision.** It is mitigated rather than eliminated, and the mitigations are
specific: the viewer builds its DOM with `createElement` and `textContent` only, sets SVG
geometry through presentation attributes, and ships a `Content-Security-Policy` meta tag
with `default-src 'none'` and no `unsafe-inline` in `script-src`. Under that policy an
injected `<script>` string does not execute even if a bug puts one in the DOM. The
generator's own posture is untouched: nothing in the Go binary renders HTML, and `go.mod`
still has no `require` block.

**The `graph.json` contract stops being a cross-repository release problem.** The exporter
and its only consumer now change in the same commit and are reviewed together. The JSON
export is still treated as a stable interface for external consumers — that was never only
about the viewer — but a schema change no longer needs two releases to land.

**Pages now deploys on every push to the default branch**, where it previously filtered on
`site/**`. The graph is derived from the whole tree, so any commit can change it, and a
`paths:` filter that listed source directories would silently go stale the first time a new
one was added. The bundle-rebuild commit cannot be used as the trigger instead: it carries
`[skip ci]` by design ([ADR 0005](0005-commit-the-bundle-to-the-repository.md)), which
suppresses every workflow. The cost is a deploy per push for a static site that is off the
merge path.

**The deploy job now builds the Go binary and checks out full history.** `fetch-depth: 0` is
required, not a precaution: co-change edges come from `git log`, so a shallow clone would
publish a graph that is quietly missing an entire edge kind rather than one that fails.

**`site/graph.json` is generated and gitignored, which makes it the one artifact in this
project that is not committed.** That is deliberate and it is the opposite of the choice in
ADR 0005. The bundle is committed because its value is that it survives without the tool
installed; `graph.json` has no value without the page that reads it, and committing it would
add a second artifact that can be stale in a repository whose central claim is that stale
fails loudly. Locally, `signpost export -format json -o site/graph.json` produces it.

**The viewer is still optional and the generator is still complete without it.** This was
the honesty test in 0006 and it does not change: `index.md` with its Mermaid graphs, the
GraphML export, and the structural findings written as text are all unaffected. Nobody has
to deploy a site.
